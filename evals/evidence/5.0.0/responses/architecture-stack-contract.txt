先给出带约束的架构决策和验证方案，不购买服务、不部署。私有客户记录使该产品至少按 R2 设计，关键权限与数据边界不能留给实现时猜测。

在现有简报中确认预算上限 B、可部署环境、操作负责人、预期用户/数据量、并发、可接受延迟、数据地域/保留周期、备份与恢复目标。未知量标为假设。成本模型应计入计算、数据库、备份、流量、身份能力、观测和维护，并留余量；没有当前官方价格和支持版本核实前，不宣称选型已满足预算。

比较两种团队可维护的候选即可：
- Python 单体、服务端页面加适量 TypeScript：部署组件少，适合小预算与简单流程；交互复杂度或独立客户端需求可能形成限制。
- Python API 加 TypeScript 前端：前后端边界清楚，适合复杂交互；构建、部署、鉴权与联调成本更高。

初步优先考察单体和支持事务的关系库，最终由部署适配、权限能力、数据一致性、维护负担、总成本和退出成本决定。框架、数据库及托管方案均为待证实候选；在真正选定依赖前核实一手支持信息，不因团队会两门语言而强加两个服务。

交付简短 ADR，说明选择、替代项、取舍、成本假设、责任人和重审触发条件；附数据流/信任边界图及这些合同：客户记录的 ID、归属/租户边界和生命周期，角色×操作权限，API 输入/输出/错误与兼容性，事务/并发不变量，以及超时、重复请求、依赖故障和恢复路径。敏感记录最小化采集；服务端逐操作鉴权，验证越权拒绝，避免日志泄露，并明确传输/静态保护与备份访问边界。

如关键边界仍不确定，提出有时间/成本上限的本地合成数据纵向探针：Web 操作→校验与鉴权→持久化→重新读取，并覆盖另一身份不可访问和失败恢复。探针尚未执行；即使通过，也只证明该环境下的路径，不能证明容量、安全完备或生产可用。后续实施采用 R2 规格/执行计划及相应安全、负路径、端到端、独立审查和恢复门槛；生产发布仍需独立授权。
