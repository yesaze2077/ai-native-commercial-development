已批准需求继续以外部工单为唯一权威；Git 保存实现及持久审计记录。每一种产物各有一个明确的权威位置，不把同一需求复制成两份可独立编辑的“最终规格”。

具体处理如下：

1. 在现有 lineage 登记中记录外部系统、稳定工单 ID、需求版本、批准者及批准记录。按组织数据策略，在 Git 留存不可变快照、内容摘要或指向固定版本的引用；不把敏感工单内容未经许可提交进仓库。
2. Git 中的规格细化或执行计划明确引用所依据的外部需求版本；若现有工单已足够表达普通功能的验收和验证计划，就直接复用，仅补缺口。代码变更引用计划或规格，测试证据引用确切代码修订，独立审查及发布记录继续引用其上游产物，形成可追溯父子链。
3. 在 ARTIFACT_LINEAGE 类登记中为需求、计划、代码、验证、审查和发布分别写明权威系统、稳定 ID 或路径、父产物、快照或 commit、负责人、批准证据及替代关系。可以更新现有等效记录，不必再建一套并行台账。
4. 只有外部写入已获授权且系统支持时，才把对应 commit SHA 回写工单；否则只在本地记录“待回链”的工单、SHA 和负责人，留给有授权的人处理。本地实现授权不自动包含外部工单写权限。
5. 如果 Git 快照与外部需求冲突，先由需求权威方确认并记录解决结果，再推进依赖该决定的实现或发布；不能悄悄选择方便的一版。需求更新后保留被替代版本，评估已有代码和验证证据是否仍适用。

功能风险需依据实际权限、数据和影响判定；普通功能可走 R1，有敏感边界则升级。本例没有实际工单、仓库或授权记录，因此以上是处理方案，尚未保存快照、建立真实回链或写入外部系统。
