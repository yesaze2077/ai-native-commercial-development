先冻结接口和写入边界，再用最少的并发写入者。对独立开发者，通常先尝试两个写入任务；若协调与整合成本超过节省时间，保持串行。

实际功能范围尚未给出，以下是分工协议，文件名和验收应从已接受的需求及代码边界中填入，不能先假定两个模块彼此独立。

| 工作 | 负责人和边界 | 开始条件与交付 |
|---|---|---|
| 契约与拆分 | 主代理，串行完成 | 确认风险、验收、输入输出、错误行为和共享接口；画依赖关系，固定基准提交 |
| 实现 A | 写入者 A，仅修改分配的模块及其独立测试 | 能在冻结契约下独立完成；交付提交或补丁、检查证据和限制 |
| 实现 B | 写入者 B，仅修改另一模块及其独立测试 | 与 A 无未解决依赖或重叠写入；同样交付独立可验证结果 |
| 整合与审查 | 一个整合负责人，随后独立审查上下文 | 按依赖顺序整合，在组合状态验证完整受影响流程 |

每个并发写入者使用独立分支和 Git worktree，不能同时修改同一个 checkout。还要分别隔离环境文件、端口、测试数据库或 schema、缓存、队列、浏览器配置和临时目录；worktree 只隔离文件，不能自动隔离这些共享状态。共享锁文件、数据库迁移和接口定义由指定负责人串行维护；需要改变冻结契约时，写入者停下并交给协调者重新拆分。

每份任务包应记录目标、风险与批准责任人、依赖、冻结契约、允许/禁止修改的路径、工具与外部操作边界、凭据和数据范围、验收、检查命令、资源命名空间、预期证据及停止条件。用现有执行计划记录依赖、资源和整合状态；若项目已有并行执行板，沿用该板，避免另建第二套可编辑记录。

整合负责人核对基准、差异范围和无关改动，按顺序整合。各分支通过后，仍须对组合状态运行受影响的回归、契约及适用构建/关键流程检查，并做独立的组合差异审查。共享部署、迁移、发布标签和生产写入保持串行，写入者不能自行合并到 main。

独立开发者仍承担产品与发布决策，可以借助新上下文独立审查，无须为每个角色常驻一个代理。此阶段生产写入者为零。记录预估串行时间、实际耗时、整合时间、冲突、返工、缺陷、模型成本和本人审查时间，再决定并行是否有收益；代理数量不能作为效率证明。

目前未创建分支、启动代理或实施功能；这是可落地的拆分方案，具体写入范围要由实际功能与仓库结构确定。
