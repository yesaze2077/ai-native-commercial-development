# Experience and Visual Design

## Mode and applicable inputs

Use for a new interface, a changed journey, or an experience review. Read the accepted outcome, affected roles, current interface and brand/component assets first. New products need the core journey defined; increments need only the affected steps and adjacent transitions. A review remains read-only. Apply [commercial-quality-gates.md](commercial-quality-gates.md) and the existing risk classification without adding a compulsory design tool or approval at every step.

## Working method

1. **Map the journey before drawing screens.** Describe actor, entry trigger, prerequisite, steps, success outcome and recovery/exit. Include the support or administrator handoff when the user cannot finish alone. Mark the uncertain or costly step that the design must resolve. For an existing product, record the relevant before/after behavior.
2. **Derive information architecture.** Group information and actions by user task; name navigation destinations, object ownership and role visibility. Define how users find an item, understand its status and return to their work. Keep terminology consistent with the product/domain model. Avoid new navigation or features unrelated to the accepted outcome.
3. **Specify states, not just the happy screen.** For each affected page or component, identify its trigger, visible information, primary action, transition and recovery. Cover applicable loading, first-use/empty, no-results, validation, partial/stale data, network/server error, permission denial and expired session states. For destructive actions, show consequence and scope before confirmation, with undo or recovery where supported. UI hiding never replaces server authorization. Explain disabled controls and preserve recoverable input after failure.
4. **Prototype the decision that remains uncertain.** Use a paper/wireframe sequence, clickable local HTML, existing component sandbox, or the user's available design workflow. Exercise the critical journey and the highest-risk alternative/failure state. Prefer an executable prototype when interaction or state is the uncertainty; use a visual mockup for hierarchy and appearance. Keep its data and integration boundaries explicit. A prototype is not production capability.
5. **Establish a small visual system.** Reuse the brand and existing components before inventing a style. Record only needed tokens: typography, color/contrast, spacing, layout widths, radii, interaction/focus and motion. Specify hierarchy and content density with representative real-length content. Check narrow/wide layouts, keyboard order, visible focus, labels, error association, screen-reader semantics, reduced motion and touch targets as applicable. Loading and feedback must remain perceivable without relying on color alone.
6. **Translate design into acceptance.** Map each critical state/interaction to its implementation location and acceptance check. Render the actual code at representative viewport sizes; walk through navigation, form submission, failure and recovery using relevant roles. Compare hierarchy, spacing, content and behavior against the selected design, capturing version-bound screenshots or recordings where useful. Resolve material differences or record an intentional decision; do not claim visual verification from source inspection alone.

If the user has a suitable design, prototype or frontend skill, route the relevant work through it while preserving this contract. If it is unavailable, proceed with an appropriate local wireframe, HTML prototype and browser checks. Do not claim Figma work, user testing, accessibility conformance or usability validation that did not happen. An agent walkthrough supports scenario coverage; observed representative users support only the tasks and sample actually studied.

## Outputs and exit basis

Add the journey, compact navigation/state map, chosen prototype or references, relevant tokens and design-to-code acceptance to the existing specification/design document. Keep one authoritative design reference and record its version. Separate proposed design, implemented interface and observed validation results.

For dependent implementation, the critical journey and applicable failure states must be specified, and material interaction choices must be resolved or have an explicitly authorized bounded alternative. Record the versioned key-screen/flow and visual baseline chosen by the user or authorized responsible owner, or the scope of their delegation. An open question affecting user outcomes, permissions, data or acceptance blocks its dependent implementation; simply listing it cannot close that handoff. Routine reversible presentation details remain within existing authorization, and read-only review may finish with clearly pending findings. Reuse an approved unchanged design for clear small changes.

Exit implementation verification only after actual rendered/interaction checks support the claim. Compare against the chosen baseline; material technical constraints changing that baseline return to its owner decision under [lifecycle-handoffs.md](lifecycle-handoffs.md). Unavailable devices, assistive technology or user access remain named limits, with the next useful check and owner. A polished screenshot alone does not establish a usable journey or business acceptance.
