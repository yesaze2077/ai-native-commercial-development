- Date: 2026-11-13 (Asia/Shanghai).
- Authorization: implement automatic assessment of actual-use boundaries, feature feedback and corrections; propose improvements and update active rules only after the user confirms the concrete change.
- Baseline: 6.0.0, commit `b1c6d57`; existing 105 tests and accepted 28-case evidence retained.

- Hypothesis: a small redacted event ledger, explicit project-versus-rule triage, decision suppression and outcome follow-up makes reusable improvements traceable without repeating advice or turning one-off product failures into universal rules.

- Stop/reversal: unresolved material correctness/privacy/control findings prevent installation. Restore coherent 6.0.0 archive when authorized; never silently revert future installed rules.

## Results

### Implemented behavior

- Added `references/usage-feedback-loop.md`, `scripts/feedback_loop.py`, redacted event example and tests. Actual-use checkpoints capture only material feedback, distinguish project/product/environment fixes from reusable workflow changes, deduplicate occurrences and prepare concrete proposals. The user confirms exact scope/diff before active rule updates; silence or a ledger field is not approval.
- Private local state lives outside the package and business repositories. The CLI only records events/decision history or assesses; it has no rule writer, patch applier, external call, scheduler or rollback command. `rule_update_authorized`, `may_update_rules` and `rules_changed` remain false during assessment.
- Unknown/conflicting causes and serious unverified claims remain investigation; ordinary one-off workflow issues remain observations. Independent recurrence/verified consequences can justify a scoped trial; cross-project candidates need independent observed support, while explicit durable preferences still produce proposals rather than approval.
- Deferred/rejected unchanged proposals stay suppressed; genuinely new material can reopen review without counting the same occurrence twice. Applied records lead to monitoring, positive observations do not become failure counts, and adverse outcomes trigger review rather than automatic rollback. Input labels and recording order never establish causality.
- New rules may replace or remove ineffective rules rather than accumulate process. Current product work keeps its existing authorization and is not blocked by optional governance suggestions. Risk/security/commercial/CI/hosted trust controls remain; the existing self-evolution reference now routes actual-use capture into this explicit confirmation loop.
