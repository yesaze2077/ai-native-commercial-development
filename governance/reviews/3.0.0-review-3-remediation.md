## 5. M1 closure: bounded streaming and process termination

Code inspection of `scripts/run_behavior_evals.py` found:

- `Popen` uses pipes and `start_new_session=True` on POSIX.
- `selectors.DefaultSelector` drains stdout and stderr while the process is running.
- stdout is accumulated in chunks of at most 65,536 bytes and checked immediately after each chunk; it is no longer captured without a bound and checked only after exit. The temporary retained amount may exceed the configured cap by at most one read chunk before rejection.
- On timeout or stdout overflow, POSIX sends `SIGKILL` to the original process group with `os.killpg(process.pid, ...)`, including when the group leader has already exited but a child still holds stdout.
- stderr chunks are drained but never appended to retained output and are withheld on non-zero runner exit.

Verification:

```bash
python -B -m unittest discover -s tests -v
```

Result: PASS, **46/46**, including `test_live_runner_output_limit_is_enforced` and the new `test_output_limit_terminates_child_process_group`.

Temporary stress tests:

1. A live adapter wrote about 6 MB of `SECRET_SENTINEL_9f3a` to stderr, then returned a 21-byte valid stdout response. The runner completed in about 0.6 seconds with exit 0; the marker did not appear in the saved raw response or report.
2. An adapter spawned a child, exited, and left the child holding stdout. The child wrote 200,000 bytes and was scheduled to create a sentinel after two seconds. With `--max-output-bytes 32`, the runner returned exit 2 in about 0.6 seconds with `exceeds 32 bytes`; after three seconds, the child sentinel did not exist.

Conclusion: review-2 M1 is closed for the tested POSIX launcher boundary. This is still a trusted launcher, not a sandbox: a deliberately detached process, non-POSIX descendant semantics, filesystem/network access, and host credentials require external isolation.
